# 修复计划（plan1）
本计划面向 `card-game` 项目中“取消后仍执行/状态不一致”的高危缺陷。要求：只输出计划，不直接改代码。

## 1. 目标与验收标准
### 1.1 目标
- 统一“取消”的语义：取消必须使对应流程彻底终止，并恢复到一致、可继续游戏的状态。
- 消除“取消越权”（取消可以跳过代价/后续步骤）与“取消不生效”（取消未清理关键状态、仍能继续执行）的路径。
- 降低重复执行/误拒绝执行的概率，避免玩家操作无响应或重复触发造成状态错乱。

### 1.2 验收标准（可观察行为）
- 在任何多阶段流程中点击取消，都不会导致后续仍能确认执行该流程的核心效果。
- 取消后 UI 不应残留“确认按钮/选择弹窗”，状态不应阻塞其他操作。
- 取消不会留下已发生的“不可回滚副作用”（例如已移动的牌）而逻辑上当作取消。
- 同一动作重复点击不会造成重复执行；不同动作不会被误判为重复而被吞掉。

## 2. 优先级与修复顺序
### P0（必须先修，危害最大）
1) 滔乱（taoluan）取消越权  
2) 密诏（mizhao）取消不回滚副作用  
3) 利驭（liyu）选牌阶段取消失效  

### P1（建议跟进，风险较高）
4) 幂等机制（lastActionId）全局单字段带来的误拦截/漏拦截  

## 3. 缺陷清单与修复方案
### 3.1 P0-1：滔乱取消越权（可跳过“他人选择代价/交牌”等后续）
#### 现象与风险
- 当前 `taoluanCancel` 仅检查 `sourceID`，不检查 `stage/played`。一旦玩家已经“打出牌并产生等待/后续步骤”，仍可直接 `G.taoluan=null` 结束流程。
- 风险：玩家在获得牌或效果后通过取消跳过“代价”（例如让对方选择、对方交牌/掉血）或跳过正常推进，属于规则破坏级漏洞。

#### 修复原则
- 取消只能在“未产生不可逆副作用”阶段允许；一旦进入 `played=true` 且需要对方选择/结算后续，则取消要么：
  - 不允许（直接 return，并给出日志提示）；要么
  - 允许但必须执行回滚（若可回滚）并恢复 `taoluanGlobalUsedNames` 等占用资源。

#### 具体改动计划（逻辑层）
- 为 `taoluanCancel` 增加阶段白名单，例如仅允许在：
  - `stage: select_card`
  - `stage: select_virtual`
  - `stage: select_targets` 且 `played=false`
- 对于 `played=true` 或 `stage` 属于以下集合时禁止取消：
  - `waiting_resolution`
  - `after_choose_other`
  - `other_choose_option`
  - `other_give_card`（如存在）
- 若禁止取消：写入 `G.actionLog.push('当前阶段不可取消滔乱')`，并保持状态不变。

#### 具体改动计划（UI 层）
- 仅在允许取消的阶段展示“取消滔乱”按钮，避免 UI 引导用户点出无效路径。
- 若点击后被后端拒绝，UI 需保持一致（按钮仍在/或按状态更新消失），并可通过 actionLog 展示原因。

#### 回归点
- 滔乱从“选牌/宣言”阶段取消：应释放 `taoluanGlobalUsedNames` 的占用（当前已做，但需确认所有早退路径）。
- 滔乱已出牌并触发 `pendingEffect/selectCard/harvest` 等等待状态时：取消不应允许绕过后续。

### 3.2 P0-2：密诏取消不回滚（副作用已发生但仍可取消）
#### 现象与风险
- `mizhaoConfirmTargetA` 会把发动者所有手牌转移给 A，但 `cancelMizhao` 只是重置状态，不回滚手牌转移。
- 风险：玩家可在进入 `selectB` 后“取消”，导致牌已转移但流程被标记为取消，产生严重状态不一致（并可能被滥用）。

#### 修复原则
- 一旦产生不可逆的主要副作用（手牌全转移），取消必须：
  - 不允许；或
  - 允许但必须回滚（把这批移动的牌归还给发动者）。

#### 具体改动计划（两种方案二选一，推荐 A）
- 方案 A（推荐）：按阶段限制取消
  - 仅允许在 `stage: selectA` 阶段取消。
  - 在 `stage: selectB` 阶段取消直接拒绝，并写入 actionLog 提示“已交出手牌，无法取消”。
- 方案 B：实现可回滚取消
  - 在 `mizhaoConfirmTargetA` 时记录 movedCards 的 card.id 列表到 `G.mizhao.movedCardIds`（或 `G.mizhaoMovedCardsSnapshot`）。
  - `cancelMizhao` 若处于 `selectB`：从 targetA 手牌中按 card.id 找回这些牌并归还 source；找不到则保持一致性策略（例如尽力回收、并记录日志）。
  - 难点：targetA 在 `selectB` 期间可能已经打出/弃置/转移这些牌，回滚会复杂且易产生新 bug。

#### UI 配套
- 在 `selectB` 阶段隐藏“取消”按钮（若采用方案 A）。
- 在行动日志清晰提示“此阶段不可取消”的原因。

#### 回归点
- `selectA` 取消：不应改变任何手牌/状态。
- `selectA` → `selectB` 过程中：取消路径要么彻底禁用要么严格回滚。

### 3.3 P0-3：利驭选牌阶段取消失效（取消后仍可继续执行）
#### 现象与风险
- 利驭进入选牌弹窗后，UI 的取消调用 `moves.cancelLiyuTarget()`，但该 move 只清理 `G.liyuTargeting`，不清理 `G.liyuCardSelecting`。
- 风险：用户以为取消了，但状态仍在；后续仍可能确认获得牌，属于“取消后仍执行”的直接来源。

#### 修复原则
- 每个阶段的取消按钮必须对应清理该阶段的状态；同名 cancel 不应只清理前置阶段。

#### 具体改动计划（逻辑层）
- 新增 move（例如 `cancelLiyuCardSelecting`）：
  - 若 `G.liyuCardSelecting.active`：将其置空/重置为 inactive；
  - 不影响其他状态机。
- 或增强现有 `cancelLiyuTarget`：同时清理 `G.liyuTargeting` 与 `G.liyuCardSelecting`（更简单，但语义更“全局取消”）。

#### 具体改动计划（UI 层）
- 选牌弹窗 `onCancel` 改为调用能清理 `liyuCardSelecting` 的取消 move。
- 目标确认区的取消按钮仍调用“取消目标选择”。

#### 回归点
- 取消后弹窗消失，且不能再触发 `liyuObtainCard`（后端也需校验 active 状态）。
- 取消后不应影响其他技能/卡牌流程。

### 3.4 P1：幂等机制 lastActionId 的单字段风险（误拦截/漏拦截）
#### 现象与风险
- `player.lastActionId` 作为全局幂等标记，被多种 move 复用（摸牌、换将、手气卡等），actionId 生成方式不一致，有的仅 `Date.now().toString()`，存在碰撞概率。
- 风险：
  - 不同动作在同一时间片发生碰撞 → 后一个被误判为重复而吞掉（用户感知为“点了没反应”）。
  - 单字段覆盖导致幂等窗口不稳定，对重复执行的防护有限。

#### 修复方向（不在本轮 P0，但建议纳入）
- 将 `lastActionId` 改为按动作类别分桶，例如 `lastActionIds: { drawCard, useLuckCard, changeGeneral }`。
- 统一 actionId 生成策略：使用更低碰撞概率的 UUID（或至少 `Date.now()+random+counter`）。
- 在关键 move 增加幂等校验或服务端去重策略，避免多次点击造成重复执行。

## 4. 实施步骤（落地顺序）
1) 为每个多阶段流程补一份“阶段图”与“副作用清单”（哪些阶段产生不可逆副作用）。  
2) 按 P0 顺序逐个修复：
   - 滔乱：限制取消阶段 + UI 隐藏不合法取消入口。
   - 密诏：选择方案 A（推荐）或 B；优先保证一致性。
   - 利驭：补齐选牌阶段取消清理。
3) 为每个修复点添加最小化自动化测试或手工复现脚本步骤（见第 5 节）。
4) 跑一轮“取消一致性”回归：所有取消按钮都应清理对应状态，且不会遗留阻塞或可继续执行的入口。

## 5. 验证与测试计划
### 5.1 最小手工用例（每个缺陷至少覆盖）
- 滔乱：
  - 在“宣言/选目标”阶段取消：应完全退出且释放占用。
  - 在“已出牌等待对方选择/等待结算”阶段尝试取消：应被拒绝，且流程继续要求完成后续。
- 密诏：
  - `selectA` 阶段取消：不转移牌。
  - `selectB` 阶段取消：按方案 A 必须不可取消；按方案 B 必须回滚已转移手牌。
- 利驭：
  - 进入选牌弹窗点击取消：弹窗关闭且后端状态清空；不能再确认获得牌。

### 5.2 自动化建议（可选）
- 在 Game.js 层写纯函数式单元测试（构造 G 初始状态 → 调用 move → 断言状态）。
- 对每个流程断言：
  - “取消后关键状态字段为 null/active=false”
  - “取消后不会留下已执行副作用（或按规则不允许取消）”

## 6. 风险控制
- 优先选择“阶段限制取消”的方案（如密诏方案 A），避免回滚复杂度引入新 bug。
- 对所有 move 增加 guard：在执行关键动作前校验当前阶段/active，避免 UI 错误调用导致越权执行。
- 对推进函数（advance*）依赖的状态字段做一致性检查，确保取消会触发必要的推进或不会让流程卡死。
